# RAG 文档编写指南

本项目的 RAG 文档是可上传到管理员后台的 `.md` 文件。每个文件代表一份独立资料，**文件名是稳定文档标识**：同名再次上传会覆盖旧文档，改名会新增文档。

## 文件格式

推荐使用 YAML front matter，并以清晰的二级标题组织资料：

```md
---
title: A 项目技术复盘
description: 首屏性能优化、设计系统与量化成果。
---

# A 项目技术复盘

## 背景与职责

说明项目背景、本人职责和约束条件。

## 技术方案

说明关键方案、取舍和实施过程。

## 成果与复盘

只写可确认的结果、数据和经验。
```

- `title`：后台与引用显示的标题；缺失时使用第一个一级标题。
- `description`：后台显示的简介；缺失时使用正文首段。
- `##`：父块边界。每个二级标题最好聚焦一个主题，例如“项目背景”“技术方案”“量化成果”。
- 正文以自然段表达完整事实。系统会从父块派生小型检索子块，并在回答时回传完整父块。
- 代码块和表格应保持完整，不要为了切分插入无意义空行。

## 内容边界

只写可以由原始简历、项目材料、公开作品或本人确认的信息支撑的事实。避免把愿望、推测和未验证的量化数据写入语料；RAG 会把文档当作回答依据。

建议一份文件只聚焦一类资料：一份简历、一项项目复盘、一组技能说明或一段教育经历。单文件最大 256KB；一次最多上传 20 份、总计不超过 1MB。

## 交给 Codex 的生成指令

将以下内容与原始材料一并交给 Codex：

```text
请只依据我提供的原始材料，生成一份可上传到本项目 RAG 后台的 Markdown 文档。

要求：
1. 输出 YAML front matter，包含 title 和 description。
2. 使用一个一级标题与多个二级标题；每个二级标题只覆盖一个清晰主题。
3. 保留明确的时间、职责、技术方案和可验证数据；不得补写、猜测或美化未提供的事实。
4. 用完整自然段表达，避免把无关主题混在同一章节。
5. 仅输出 Markdown 文件内容，不附加解释。
```

上传前先在后台执行预检，确认父块/子块数量与预估 embedding 成本；确认后才会调用模型并写入 COS。
